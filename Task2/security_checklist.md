**Инфраструктура.** Собственный ЦОД, приватное облако и арендованные мощности облачного провайдера (гибрид). Облако временно используется для разработки и тестирования. Внешние пользователи заходят через межсетевой экран. Все БД резервируются на нужную глубину.

## 2. Выбор разделов проверочного листа и обоснование

Разделы выбраны по двум глобальным проблемам компании (нарушен контроль данных, нет политик для API партнёров) и по четырём бизнес-потребностям аудита. Это удовлетворённость клиентов, развитие BI/ML/AI, предотвращение утечек и соответствие законодательству РФ.

| Раздел | Приоритет | Включён | Почему |
|---|---|---|---|
| I. Управление доступом | Высокий | Да, полностью | В ЛК клиентов отображаются чужие ФИО — это прямой признак ошибки авторизации (доступ к объекту чужого пользователя). Есть несколько точек регистрации и несколько несвязанных реестров учётных записей: Keycloak, два AD, client-crm, CRM собственников. Партнёр одной УК может видеть и менять данные другой УК. После смены руководителей IT-команд нет уверенности, что права пересмотрены и отозваны |
| II. Безопасность данных | Высокий | Да, полностью | Ключевая проблема компании. Классификации данных нет, потоки данных контролируются не системно. Сырые ПДн из всех БД попадают в Greenplum без ограничений доступа. Отсутствие Data Governance блокирует BI/ML/AI-продукты. Утечка у конкурента показывает цену ошибки |
| III. Защита инфраструктуры | Средний | Да | Инфраструктура гибридная: свой ЦОД, приватное и арендованное облако, временные облачные ресурсы для разработки и тестирования. Из защиты известен только межсетевой экран на входе. Нужно проверить сегментацию (особенно изоляцию хранилища данных и БД с ПДн), фильтрацию трафика к партнёрам и контроль облака. Приоритет средний: прямых инцидентов на уровне сети в кейсе нет |
| IV. Управление инцидентами | Высокий | Да | Жалобы на чужие данные в ЛК остаются без найденной причины — это значит, что инциденты не выявляются и не расследуются системно. По 152-ФЗ (ст. 21 ч. 3.1) об утечке ПДн нужно уведомить РКН в течение 24 и 72 часов, без процесса реагирования это невыполнимо |
| V.1. Специфические аспекты: общие вопросы | Средний | Да | Нужен для гибридного облака: резервное копирование в облаке, защищённые каналы между ЦОД и облачным провайдером, удалённый доступ команд |
| V.2. Оборудование и физическая безопасность | Низкий | Нет, отложен | В кейсе нет данных и нет проблем, связанных с физической безопасностью ЦОД. Описанные проблемы лежат на уровне приложений, данных и интеграций. Раздел рекомендуется проверить отдельным аудитом ЦОД, вопросы приведены в конце для полноты |
| **VI. Безопасность API и внешних интеграций** (добавлен) | Высокий | Да, новый раздел | Вторая глобальная проблема компании. Контракты API содержат ПДн, нет единых политик безопасности и изоляции данных между УК. Компания планирует развиваться за счёт партнёрских сервисов, поэтому риск будет расти. В шаблоне этих вопросов нет |
| **VII. Соответствие законодательству РФ** (добавлен) | Высокий | Да, новый раздел | Бизнес-потребность «проверить соответствие требованиям законодательства». Компания обрабатывает ПДн, включая паспортные данные и СНИЛС, взаимодействует со СМЭВ и использует арендованное облако. Нужно проверить 152-ФЗ, требования ФСТЭК и ПП № 1119, а также локализацию ПДн |
| **VIII. Процессы ИБ и управление изменениями** (добавлен) | Высокий | Да, новый раздел | Специалист по ИБ один на всю компанию, и ему передают не все решения и изменения. Пока ИБ не встроена в процесс изменений, любые технические меры будут обходиться при разработке |

**Условные обозначения в столбце «Да/нет»:**
- **Да** — мера реализована;
- **Частично** — реализована не во всех системах или без процесса;
- **Нет** — по описанию и диаграмме мера отсутствует;
- **Нет данных** — информации недостаточно, вопрос нужно уточнить на интервью с командами в ходе аудита.

Интеграции с УК, платёжной системой и СМЭВ идут без единых политик безопасности и без API-шлюза. Нужно проверить временные облачные ресурсы для разработки и тестирования |

Координации между точками регистрации нет. Сотрудники заведены в двух AD. Это вероятная причина показа чужих ФИО в ЛК (неверное сопоставление записей) |

| 14  | Используются ли средства централизованного контроля доступа? | Нет | Нет единого IAM/SSO для всех доменов, нет централизованной авторизации API. Хранилище данных доступно без ограничений |
