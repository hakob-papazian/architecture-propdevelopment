## 1. Контекст и ключевые архитектурные решения

Партнёр предоставляет облачную платформу «Умный дом» и устройства: интеллектуальный домофон с распознаванием лиц и интеллектуальный шлагбаум с распознаванием номеров. Собственники пользуются новыми функциями в существующем мобильном приложении «Витрина сервисов для собственников».

| № | Решение | Почему |
|---|---|---|
| AD-1 | Вся интеграция с партнёром идёт через новый сервис **smart-home-service** (anti-corruption layer). Мобильное приложение не вызывает API партнёра напрямую, кроме медиапотока и регистрации лица (AD-3) | Единая точка контроля передаваемых данных, прав доступа и журналирования. В Task2 выявлено, что сейчас интеграции с партнёрами не контролируются системно |
| AD-2 | Новый **API Gateway** — единая точка входа для мобильного приложения и входящих webhooks партнёра | Централизованная проверка токенов, mTLS, rate limiting, WAF и журналирование (пробелы Task2 VI.2, III.12). Существующие маршруты приложения к tenant-core-app и CRM рекомендуется перевести на этот же шлюз позже |
| AD-3 | **Биометрия и видео не проходят через системы PropDevelopment.** Фото для регистрации лица и видеопоток домофона приложение передаёт напрямую на платформу партнёра по одноразовому токену, который выдаёт smart-home-service. PropDevelopment хранит только идентификатор шаблона (`face_template_id`) | Биометрия — особая категория ПДн (152-ФЗ, ст. 11, «секретные данные» по Task1). Чем меньше систем её касается, тем меньше область риска утечки и тем проще выполнить требования закона |
| AD-4 | Партнёр получает только **псевдонимизированные данные**: `resident_id` (UUID), идентификаторы ЖК, подъезда и квартиры, номера авто. ФИО, телефон, e-mail и паспортные данные не передаются | Минимизация данных (152-ФЗ, ст. 5). Устраняет проблему «контракты API содержат ПДн» |
| AD-5 | Партнёр видит и изменяет **только объекты ЖК, где установлены его устройства**: изоляция по `complex_id` в каждом токене и каждом запросе | Устраняет проблему «партнёр одной УК видит данные другой» |
| AD-6 | **smart-home-db не реплицируется в хранилище по CDC.** В аналитику попадают только обезличенные агрегаты (например, число проходов по подъезду за час) | Не повторять ошибку с сырыми ПДн в Greenplum |
| AD-7 | Секреты интеграции хранятся в **Vault**, журналы безопасности собираются в **SIEM** | Управление ключами и мониторинг (пробелы Task2 II.3, IV.1) |

## 2. Изменения в диаграмме контейнеров

**Новые контейнеры** (группа «Умный дом», домен ЖКУ):

| Контейнер | Технологии | Ответственность |
|---|---|---|
| API Gateway | Kong / NGINX + WAF | TLS-терминация, проверка JWT (JWKS из auth-service-1), mTLS для партнёра, rate limiting, защита от OWASP API Top 10, журналы доступа |
| smart-home-service | Kotlin, Spring Boot | Права доступа жильцов, членов семьи и гостей; номера авто; команды открытия; выдача одноразовых токенов медиасессий; приём и обработка событий партнёра; отзыв доступа при смене собственника |
| smart-home-db | PostgreSQL | Связь `resident_id` ↔ собственник/квартира, права доступа, номера авто, `face_template_id`, согласия на обработку биометрии, журнал событий (срок хранения ограничен) |
| notification-service | Kotlin, Spring Boot | Push-уведомления о вызове домофона и проходах. В тексте push нет ПДн, детали приложение запрашивает после аутентификации |
| Secrets Vault | HashiCorp Vault | Клиентские сертификаты mTLS, OAuth client secret, ключи HMAC для webhooks, автоматическая ротация |
| SIEM | MaxPatrol SIEM / ELK | Корреляция событий gateway, smart-home-service, Keycloak; оповещения об аномалиях |

**Новые внешние системы:** платформа «Умный дом» партнёра, интеллектуальный домофон, интеллектуальный шлагбаум, сервисы push (APNs/FCM), ЕБС (при необходимости, см. SEC-B4).

**Изменённые элементы:**
- **Витрина сервисов для собственников** — новый раздел «Умный дом».
- **auth-service-1 (Keycloak)** — MFA и step-up-аутентификация для чувствительных операций.
- **Аналитик BI** перенесён на схеме ниже, чтобы освободить место. Его связь не изменилась.

## 4. Требования к безопасности

### 4.1. Общие и сетевые

| ID | Требование |
|---|---|
| SEC-01 | Весь обмен — только TLS 1.2+ (рекомендуется TLS 1.3), со стойкими наборами шифров и HSTS. Незашифрованные протоколы запрещены |
| SEC-02 | Взаимная аутентификация PropDevelopment ↔ партнёр по mTLS. У каждой стороны свой клиентский сертификат. Сертификаты хранятся в Vault и ротируются не реже раза в 90 дней |
| SEC-03 | Входящие запросы от партнёра принимаются только через API Gateway и только с разрешённых IP-адресов (allowlist) |
| SEC-04 | smart-home-service и smart-home-db размещаются в отдельном сетевом сегменте. Доступ к ним разрешён только с API Gateway; исходящий трафик — только к платформе партнёра, Vault, CRM, notification-service и SIEM |
| SEC-05 | API Gateway ограничивает частоту запросов: на пользователя, на партнёра и отдельно на команду «открыть» (например, не более 10 команд в минуту на квартиру). Подключён WAF с правилами OWASP API Top 10 |
| SEC-06 | Все API описаны в OpenAPI 3, версионируются (`/v1/...`), а входные данные проверяются по схеме. Поля, которых нет в контракте, отклоняются. Любое изменение контракта, добавляющее категории данных, согласуется с ИБ |

### 4.2. Данные и приватность

| ID | Требование |
|---|---|
| SEC-D1 | Партнёру передаётся только минимальный набор: `resident_id` (UUID, без связи с ФИО), `complex_id`, `entrance_id`, `apartment_id`, срок действия доступа, номера авто, `face_template_id`. ФИО, телефон и e-mail не передаются |
| SEC-D2 | Изоляция арендаторов. Каждый запрос и каждый токен партнёра ограничены списком `complex_id`, на которые у него заключён договор. smart-home-service проверяет принадлежность объекта до вызова и при приёме событий |
| SEC-D3 | Проверка владения объектом (защита от BOLA/IDOR). Собственник управляет только своей квартирой: `resident_id` и `apartment_id` берутся из токена и проверяются через CRM, а не из параметров запроса |
| SEC-D4 | Данные шифруются при хранении (at rest) в smart-home-db и в резервных копиях. Номера авто шифруются на уровне поля |
| SEC-D5 | Сроки хранения: журнал проходов в PropDevelopment — не более 90 дней. Видеоархив у партнёра — не более 30 дней (точный срок задаётся в договоре). После истечения сроков данные удаляются автоматически |
| SEC-D6 | При продаже квартиры, выезде жильца или отзыве согласия все права доступа отзываются немедленно. Номера авто удаляются, у партнёра запрашивается удаление биометрического шаблона, удаление подтверждается в течение 3 рабочих дней |
| SEC-D7 | Push-уведомления не содержат ПДн и фото. Например: «Вызов домофона, подъезд 2». Детали показываются в приложении после аутентификации |
| SEC-D8 | В хранилище данных передаются только обезличенные агрегаты. CDC из smart-home-db запрещён |
| SEC-D9 | Персональные данные граждан РФ хранятся и обрабатываются партнёром на территории РФ (152-ФЗ, ст. 18 ч. 5) |

### 4.3. Биометрия

| ID | Требование |
|---|---|
| SEC-B1 | Распознавание лица — добровольная функция. Перед регистрацией лица у каждого человека (собственника и каждого члена семьи) берётся отдельное согласие на обработку биометрических ПДн (152-ФЗ, ст. 11). Для несовершеннолетних согласие даёт законный представитель. Без согласия работают классический домофон, ключ и открытие из приложения |
| SEC-B2 | Фото для регистрации передаётся из приложения напрямую на платформу партнёра (SDK, HTTPS) по одноразовому токену регистрации (TTL ≤ 5 минут, привязан к `resident_id`). PropDevelopment не хранит и не пересылает изображения |
| SEC-B3 | Платформа партнёра обязана проверять «живость» (liveness / anti-spoofing) при регистрации и при распознавании: фото и видео на экране не должны открывать дверь. Пороги ложного допуска (FAR) фиксируются в договоре |
| SEC-B4 | Юридическая проверка соответствия 572-ФЗ «Об осуществлении идентификации и (или) аутентификации физических лиц с использованием биометрических персональных данных» до запуска. Если требуется, идентификация выполняется через ЕБС или партнёр подтверждает правовое основание обработки вне ЕБС |
| SEC-B5 | Биометрические шаблоны хранятся у партнёра зашифрованными, изолированно от прочих данных. Доступ к ним — только у подсистемы распознавания |

### 4.4. Устройства и физическая безопасность

| ID | Требование |
|---|---|
| SEC-I1 | Каждое устройство аутентифицируется на платформе партнёра своим X.509-сертификатом (MQTT over TLS). Пароли по умолчанию запрещены |
| SEC-I2 | Обновления прошивки подписываются партнёром и проверяются на устройстве (secure boot). Критические уязвимости устраняются в срок не более 30 дней |
| SEC-I3 | Устройства подключаются к изолированной сети или VPN партнёра. Входящие подключения из интернета к устройствам запрещены |
| SEC-I4 | Offline-режим: при недоступности платформы устройство работает по последнему загруженному списку доступа (с ограниченным сроком действия) и физическим ключам |
| SEC-I5 | Режим отказа: при пожарной тревоге и отключении питания дверь подъезда открывается согласно требованиям пожарной безопасности. Шлагбаум допускает ручное открытие для экстренных служб |
| SEC-I6 | Вскрытие корпуса устройства и попытки подбора фиксируются как событие безопасности и передаются в PropDevelopment |

### 4.5. Журналирование, мониторинг, инциденты

| ID | Требование |
|---|---|
| SEC-L1 | Журналируются все операции: выдача и отзыв доступа, команды «открыть» (кто, что, когда, с какого устройства, результат), регистрация и удаление лица, вызовы API партнёра и webhooks. ПДн в журналах маскируются |
| SEC-L2 | Журналы передаются в SIEM. Настроены оповещения: массовые команды открытия, отказы аутентификации, обращения партнёра к чужим `complex_id`, всплеск отказов распознавания |
| SEC-L3 | Партнёр уведомляет PropDevelopment об инциденте с ПДн не позднее чем через 12 часов. Это нужно, чтобы PropDevelopment уложилась в 24 часа на уведомление РКН (152-ФЗ, ст. 21 ч. 3.1) |
| SEC-L4 | Партнёр предоставляет результаты независимого пентеста платформы и устройств не реже раза в год. PropDevelopment вправе провести собственный аудит |

## 5. Протоколы аутентификации и авторизации

| Взаимодействие | Аутентификация | Авторизация |
|---|---|---|
| Собственник/житель → мобильное приложение → API Gateway | **OpenID Connect, Authorization Code + PKCE** через auth-service-1 (Keycloak). Access token — JWT со сроком жизни 5–15 минут, refresh token с ротацией и привязкой к устройству. **MFA** (SMS/TOTP/биометрия смартфона) при входе на новом устройстве. **Step-up-аутентификация** (повторное подтверждение, claim `acr`) для удалённого открытия двери, выдачи гостевого доступа, регистрации лица и добавления номера авто | **RBAC + ABAC.** Роли: `owner` (собственник), `resident` (член семьи, доступ выдаёт собственник), `guest` (временный пропуск), `uk_operator` (сотрудник УК). Атрибуты: `apartment_id`, `entrance_id`, `complex_id`, срок действия. Проверка владения объектом в smart-home-service по данным CRM |
| API Gateway ← токены приложения | Проверка подписи JWT по JWKS Keycloak, проверка `aud`, `iss`, `exp`, scope | Грубая проверка scope на шлюзе (`smarthome:read`, `smarthome:open`, `smarthome:manage`). Детальная проверка — в smart-home-service |
| smart-home-service → платформа партнёра | **mTLS** + **OAuth 2.0 Client Credentials** у сервера авторизации партнёра. Токены привязаны к сертификату (RFC 8705), срок жизни не более 15 минут | Scope по операциям (`access.write`, `door.open`, `barrier.open`, `media.session`, `enrollment.session`). Ограничение по `complex_id` из договора |
| Платформа партнёра → API Gateway (webhooks) | **mTLS** (сертификат партнёра) + **OAuth 2.0 Client Credentials** — отдельный клиент партнёра в Keycloak. Каждое сообщение подписано **HMAC-SHA256** (заголовки `X-Signature`, `X-Timestamp`, `X-Event-Id`) | Клиент партнёра может только отправлять события и только по своим `complex_id`. Защита от повторов: окно 5 минут по timestamp и уникальный `event_id` (идемпотентность) |
| Мобильное приложение → платформа партнёра (видео, регистрация лица) | **Одноразовый токен сессии** (JWT, подписан партнёром, TTL ≤ 60 секунд для видео и ≤ 5 минут для регистрации). Выдаётся через smart-home-service только аутентифицированному пользователю | Токен привязан к `call_id` или `resident_id`, к устройству и к одному подъезду. Повторное использование невозможно |
| Платформа партнёра → устройства | X.509-сертификат устройства, MQTT over TLS, взаимная аутентификация | Устройство подписано только на команды своего подъезда или въезда |
| Сотрудник УК → веб-интерфейс | OIDC через корпоративный IdP (AD/Keycloak) + MFA | Роль `uk_operator`, ограничена ЖК своей УК |

## 6. Организация взаимодействия систем

### 6.1. Принципы

- **Синхронный обмен** — REST/JSON поверх HTTPS для команд и управления правами. Для команд используются ключи идемпотентности (`Idempotency-Key`), таймауты (2–5 секунд), повторы с экспоненциальной задержкой и circuit breaker.
- **Асинхронный обмен** — события от партнёра приходят как webhooks на API Gateway. smart-home-service подтверждает получение (`202 Accepted`) и обрабатывает событие через внутреннюю очередь (Kafka). Партнёр повторяет доставку до получения подтверждения.
- **Изменения прав доступа** отправляются партнёру через transactional outbox. При недоступности партнёра изменения накапливаются и досылаются, а ежечасная сверка (reconciliation) выявляет расхождения списков доступа.
- **Источник истины** о правах доступа — PropDevelopment (smart-home-db, данные о собственности — CRM). Партнёр хранит рабочую копию для устройств.

### 6.2. Основные API партнёра (вызывает PropDevelopment)

| Метод | Назначение |
|---|---|
| `PUT /v1/complexes/{complexId}/residents/{residentId}` | Создать или обновить жильца: подъезды, срок доступа, флаг «распознавание лица разрешено» |
| `DELETE /v1/complexes/{complexId}/residents/{residentId}` | Отозвать доступ и удалить данные жильца, включая биометрию |
| `PUT /v1/complexes/{complexId}/vehicles/{plate}` / `DELETE ...` | Добавить или удалить номер авто (лимит на квартиру, срок для гостевых номеров) |
| `POST /v1/complexes/{complexId}/guest-passes` | Временный пропуск для гостя или курьера (одноразовый код, срок действия) |
| `POST /v1/devices/{deviceId}/commands/open` | Открыть дверь или шлагбаум (с `Idempotency-Key`) |
| `POST /v1/media-sessions` | Получить одноразовый токен видеосессии для вызова `callId` |
| `POST /v1/enrollment-sessions` | Получить одноразовый токен регистрации лица для `residentId` |
| `GET /v1/complexes/{complexId}/access-list` | Сверка списков доступа |

### 6.3. События партнёра (webhooks в PropDevelopment)

`intercom.call.incoming`, `intercom.call.ended`, `access.granted` (метод: face / plate / key / app / guest_code), `access.denied`, `enrollment.completed`, `biometrics.deleted`, `device.status.changed`, `device.tamper`.

Пример тела события (без ПДн):

### 6.4. Ключевые сценарии

1. **Подключение услуги.** Собственник включает «Умный дом» в приложении (OIDC + MFA). smart-home-service проверяет в CRM право собственности на квартиру, создаёт `resident_id` и регистрирует жильца у партнёра (`PUT residents`). Собственник может добавить членов семьи — каждый получает свою учётную запись и роль `resident`.
2. **Регистрация лица.** Пользователь даёт отдельное согласие на биометрию (сохраняется в smart-home-db). Приложение запрашивает токен регистрации (`POST enrollment-sessions` через smart-home-service), снимает лицо с проверкой «живости» и отправляет его напрямую партнёру. Партнёр присылает событие `enrollment.completed` с `face_template_id`.
3. **Проход по лицу.** Домофон распознаёт лицо, платформа партнёра сверяет его со списком доступа подъезда и открывает дверь. В PropDevelopment приходит событие `access.granted`, которое записывается в журнал.
4. **Вызов домофона гостем.** Партнёр отправляет `intercom.call.incoming`. smart-home-service определяет квартиру, notification-service отправляет push без ПДн. Приложение получает одноразовый токен медиасессии и подключается к видеопотоку партнёра (WebRTC/SRTP). Собственник нажимает «Открыть» (step-up при необходимости). Команда идёт через API Gateway в smart-home-service и затем в `POST commands/open`. Партнёр подтверждает событием `access.granted`.
5. **Въезд по номеру.** Собственник добавляет номер авто (step-up, лимит на квартиру). smart-home-service передаёт его партнёру. Шлагбаум распознаёт номер и открывается, приходит событие. Гостевой номер действует ограниченное время.
6. **Отзыв доступа.** CRM фиксирует смену собственника, smart-home-service получает событие и отзывает доступ всех жильцов квартиры (`DELETE residents`, удаление номеров). Партнёр подтверждает удаление биометрии событием `biometrics.deleted`. Если подтверждения нет в срок, создаётся инцидент.
7. **Недоступность партнёра.** Устройства работают в offline-режиме по кэшу списков доступа и физическим ключам. Изменения прав накапливаются в outbox. Пользователь видит в приложении статус «функция временно недоступна».

## 7. Связь требований с проблемами компании

| Проблема из кейса / Task2 | Как закрывается |
|---|---|
| Контракты API партнёров содержат ПДн | AD-4, SEC-D1, SEC-06 |

| Чужие данные в личном кабинете | SEC-D3, авторизация на уровне объекта |
| Нет единых политик безопасности API | AD-1, AD-2, раздел 5 |
| Сырые ПДн уходят в хранилище | AD-6, SEC-D8 |
| ИБ не знает об изменениях | SEC-C3 |
| Соответствие законодательству | SEC-B1, SEC-B4, SEC-D9, SEC-C1, SEC-L3 |
